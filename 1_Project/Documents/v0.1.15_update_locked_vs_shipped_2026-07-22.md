## 2. Drift-check incorporation into the plugin (this update's actual scope)

### The problem today

`drift_check.py` lives at `~/code/cowork-tools/drift_check.py` — a sibling repo to `writing-cowork`, not part of the plugin. `pm-run-drift-check` invokes it via a hardcoded host path and fails with an explicit error if that path doesn't exist. This means:

- Installing the `writing-cowork` plugin alone does **not** give a consumer a working drift check — they also need to separately clone/set up `cowork-tools`, by hand, per its own README's "Setup (per machine)" section.
- The script isn't versioned or distributed alongside the plugin at all — updates to it don't ride the plugin's release/update mechanism.

You want this fixed: the script ships **inside** the plugin, the same way `skills/`/`templates/`/`.claude-plugin/` already do, using the same `git-subdir` mechanism already adopted for `0_Product/` in the v0.1.15 restructuring.

### Proposed approach

Given `0_Product/` is already the plugin root (confirmed: `.claude-plugin/`, `skills/`, `templates/`, `Documents/` all live there, per `Decisions.md`'s "Full 0_Product consolidation" section), the natural placement is a new top-level folder inside `0_Product/`:

```
0_Product/
├── .claude-plugin/
│   └── plugin.json
├── skills/
├── templates/
├── Documents/
└── tools/                      ← NEW
    ├── drift_check.py          ← moved from cowork-tools repo
    └── README.md               ← the cowork-tools README, trimmed to drift_check.py scope
```

**Path resolution.** `${CLAUDE_PLUGIN_ROOT}` already resolves to `0_Product/` for any installed copy of this plugin (confirmed in `0_Product/README.md`). So `pm-run-drift-check/SKILL.md`'s invocation line changes from:

```
python3 ~/code/cowork-tools/drift_check.py ...
```

to:

```
python3 "${CLAUDE_PLUGIN_ROOT}/tools/drift_check.py" ...
```

This is the one substantive skill-doc edit needed to complete incorporation — everything else about the skill's behavior (arguments, registry lookup, output locations) stays the same, since the script itself isn't being changed in this pass (per your "not necessarily fix it yet" instruction).

**What does NOT move:**
- `~/.config/cowork/registry.yaml` — the per-machine registry stays external, as it must; it's user/machine state, not plugin content.
- `lift/` from `cowork-tools` — unrelated to drift check, already flagged in `Decisions.md` as "removed 2026-07-21, to be rewritten from scratch" — not part of this incorporation.
- The launchd job / plist — stays external and machine-specific; it just needs its command line updated to point at the new path once incorporation lands (a one-time manual edit per machine, or could be scripted, see open question below).

### What this does NOT do (per your "not necessarily fix it yet")

This plan moves the file and repoints the invocation path. It does **not**:
- Fix the report-filename timestamp gap (§1, confirmed still open)
- Build the self-diagnosing exclude-list mode (§3, still just a proposal)
- Touch the matcher logic, exclude-list defaults, or any check's behavior at all

Those stay separate, optional follow-on work — flagging so "incorporate" and "fix" don't get conflated the way the last roadmap draft risked doing.

### Migration concerns for existing installations

Reconciliation Hypothesis and Epistemology (and this dev repo's own launchd setup, if any) currently point at `~/code/cowork-tools/drift_check.py`. Once the plugin ships its own copy at `${CLAUDE_PLUGIN_ROOT}/tools/drift_check.py`, existing per-machine registries and launchd jobs still point at the old path and will keep working *as long as `~/code/cowork-tools/` isn't deleted*. This is not automatically a breaking change, but it does create exactly the kind of drift the plugin is supposed to prevent — two live copies of the same script, one inside the plugin cache, one at the old location, that can silently diverge if either gets edited without the other.

**Recommend:** once incorporation is verified working (via the Common Sense test project, see §4), do a deliberate one-time cutover on real machines: update `~/.config/cowork/registry.yaml`-adjacent invocation points (the launchd plist's command line, and any per-project note referencing the old path) to point at the plugin-bundled copy, then archive or delete the standalone `cowork-tools` repo's `drift_check.py` (keep the repo for `lift/` and its README/history if still wanted, or retire it entirely — your call). `pm-migrate-to-shared-tool` already exists for a related one-time migration pattern (embedded-per-project → shared script) — worth checking whether that skill's shape can be reused or extended for this specific "shared-external → plugin-bundled" migration, rather than inventing a new one-off procedure.

**Open question:** do you want a small skill/script to automate the registry/launchd repoint across machines, or is this a manual one-time edit given how few machines are actually running this (just yours)? Given the scale (one user, a small number of machines), recommend manual — building automation for a one-time, one-person migration is disproportionate.
