### `resources/` + citation ledger — scope and lifecycle decided 2026-07-22

**Scope (resolved):** the ledger tracks two things, not one — items *referenced* (cited in the manuscript, academic sense) and items *used in production* (the actual fetched/retained asset that fed the work). Both belong in the same ledger; a `kind` (or `role`) column distinguishes them rather than splitting into two artifacts, since a single resource is often both (cited AND used) and a split ledger would just require cross-referencing anyway.

**Lifecycle (resolved 2026-07-22):** resources are a cache by default, not a permanent archive. **TTL = 16 days since last access** — and "access" is genuinely any read/reference, not just incorporation into production work. This is a meaningfully harder mechanism than a simple "days since retrieved" field, worth being explicit about:

- The ledger needs a `last accessed` column, distinct from `date retrieved` (when it first entered the cache) and `date last used` (when it was actually incorporated into production/cited). Three different timestamps, three different meanings.
- Something has to *touch* `last accessed` every time the resource is opened — this isn't a passive field, it requires either (a) a skill/convention where opening a resource means running something that stamps the ledger row, or (b) reading the filesystem's own access/modify time as a proxy, which is unreliable across sync tools (iCloud, git checkouts, Obsidian indexing can all touch mtimes without a human "accessing" the content) and would need real validation before trusting it. Recommend (a) — an explicit touch, likely folded into whatever skill/convention reads from `resources/` — over relying on filesystem timestamps, since those are too easily wrong for something that drives deletion.
- 16 days is short enough that this will fire often in normal use — worth deciding now whether the cleanup step is fully automatic or requires writer confirmation (see below), since a wrong touch-mechanism at a 16-day window would surface mistakes fast rather than silently, which is actually a point in favor of starting with a short TTL: problems with the touch mechanism get caught quickly rather than lurking for months.

Any item can be flagged to opt out of the 16-day clock entirely (`retain: perpetual` or similar) — a per-row override that keeps a specific resource around indefinitely regardless of last-access. Cleanup itself should be something the writer confirms, not something that silently deletes files — a `pm-run-drift-check`-style flag in the Attention block ("N resources past their 16-day retention window, review before cleanup") rather than an automatic deletion job, at least for v0.15. Automatic deletion is real risk (destroying something the writer meant to keep but forgot to flag) for a first version, and doubly so with a 16-day window that will trigger routinely.

**Ledger schema, updated:**
`resource | kind (referenced/used/both) | source (URL or path) | date retrieved | date last used | last accessed | retain (default/perpetual) | last verified | notes`

**Still open, not yet decided:**
- The touch mechanism for `last accessed` — what actually updates it, and how reliably. This is the crux of whether the 16-day TTL is trustworthy at all; needs a concrete design, not just a column.
- Does "last verified" (source-changed staleness, separate from the access-TTL) get checked automatically (real engineering — a fetch/diff mechanism) or is it a manual "check this again in N months" prompt a human acts on? Recommend starting manual for v0.15; automatic staleness-checking is a natural v0.16+ follow-on once the ledger has real usage data.
- What actually goes in `resources/` vs. stays ad hoc — this has to be a per-vault decision documented in each writer's own `charter.md`; the plugin ships the mechanism, not the content policy.

**Git-tracked by default**, per the plugin's existing convention (nothing else in the vault is silently excluded from version control), with an explicit `.gitignore`-style opt-out for large binaries that shouldn't bloat the repo (e.g. `resources/.local/`), documented in `file_hierarchy.md`'s Conventions section the same way the scratch-folder convention already is. This is a git-tracking question, separate from the cache-lifecycle question above — worth keeping the two distinct since "committed to git" and "eligible for cache cleanup" are independent axes (a perpetual reference can still be gitignored if it's a large binary, and a cached item can still be git-tracked while it lives).

## 3. Drift-check reliability — the real blocker underneath both handoffs

**Status: read access to `~/code/cowork-tools/drift_check.py` granted and verified 2026-07-22.** Everything below marked "confirmed against source" was checked directly in the real script, not inferred from SKILL.md docs or report output.

Five separate, possibly-overlapping problems are in play:

1. **Exclude-list currency** (config problem, per-vault, no plugin change needed) — confirmed directly against Reconciliation's live `drift_check.yaml`. `bible_reference/`, `resources/Bibles/`, `handoffs/`, `recommendations/` are all missing from that vault's exclude list. 2. **Self-diagnosing stale-pattern detection** (plugin-level, genuinely new) — confirmed **not built**: no such logic exists in `pm-run-drift-check/SKILL.md`. Defaults would ship as a commented example in `templates/drift_check.yaml`; each project fills in its own list (e.g. `0_Product` here — `process/` can be split further, e.g. `process/data_management` prioritized while `process/active`/`Handoff` stay low-priority, rather than an all-or-nothing choice).

**New finding (not in either handoff): the locked cross-phase dependency check is shipped but silently non-functional against the real schema.** `check_cross_phase_dependency` (lines 512–602) is real, working, shipped code — contradicting the earlier assumption that Drift Enhancements' "ship status is unverified." But it expects `todos.md` rows in the form `| id | title | status | priority | milestone | depends-on |`, reading milestone from `cells[4]` and depends-on from `cells[5]`. The real, confirmed schema (`pm-add-task`/`pm-init-todos` SKILL.md, verified no `depends-on` anywhere in either file) is `| ID | Description | Milestone | Assignee | Status | Added | Notes |` — 9 raw cells per row once split on `|`. ## 4. Task dependency gate — design choice, not just "build the locked thing"

Flagging this as a real decision point rather than folding it silently into "finish v0.1.14." The original `ASSESSMENT_DRIFT_ENHANCEMENTS_v014.md` locked **a nightly drift-report warning** for cross-phase dependencies (advisory, surfaced in the hub Attention block, doesn't block anything). The new handoff's Fix 1 proposes **a close-time hard gate** (`pm-close-task` refuses to close unless dependencies are satisfied, requires `--force` to override). These solve related but different problems:

- The locked design catches "a dependency *formed* that changes project shape" — useful for surfacing surprises.
- The new proposal catches "someone is *about to close* a task whose dependency isn't actually done" — useful for preventing the exact I3.2/I3.3 incident (closed, then had to be manually reverted same-day).

The I3.2/I3.3 incident is a close-time failure, not a shape-change-went-unnoticed failure — the nightly-report design as originally locked would **not** have caught it, since the drift check runs on a schedule, not synchronously with the close action. **Recommendation: build both, but recognize they're additive, not redundant** — the close-time gate prevents the specific documented incident; the nightly check catches dependency changes that don't happen to line up with a close event.

**Updated per §3's source-verified finding:** the nightly check (`check_cross_phase_dependency`) is not merely unshipped — it's shipped, real code that is silently non-functional against the actual `todos.md` schema (reads the wrong columns, so it can never fire), and is additionally never enabled because the required `checks:` config block is missing from the shipped template. This means the two workstreams share more surface area than previously scoped: both need the same schema decision (does `Depends-on` get added as a real column, and where), and fixing the nightly check's dead cell-index mapping is cheap and should happen in the same pass as adding the column — doing the schema migration once and pointing both the close-time gate and the nightly check at it, rather than fixing the nightly check's indices against a schema that's about to change again. Recommend sequencing as one combined schema-migration-sized effort, not two: (a) add `Depends-on` column + migration convention for existing tasks, (b) fix `load_todos`/`check_cross_phase_dependency`'s cell indices to match, (c) add the missing `checks:` block to `templates/drift_check.yaml`, (d) add close-time precondition logic to `pm-close-task`/`pm-update-task`. Budget accordingly — this is larger than either handoff scoped it, now that the nightly check's actual state is known.
