### `resources/` + citation ledger — needs real design, not just a folder

You flagged this correctly as needing thought, not just a mkdir. The problem statement, restated from what you said: (a) avoid re-downloading/re-fetching the same reference material repeatedly across sessions, (b) track what's kept vs. deliberately not retained, (c) know when to refresh something because the external source changed.

That's three distinct behaviors a plain folder doesn't give you:

- **A ledger schema.** Minimum viable columns: `resource | source (URL or path) | date retrieved | retain? (yes/no/superseded) | last verified | notes`. Open question: does "last verified" get checked automatically (would need a fetch/diff mechanism — real engineering) or is it a manual "check this again in N months" prompt a human acts on? Recommend starting manual — a `drift_check.yaml`-style staleness check ("resource not verified in >180 days, flag in Attention") is a natural v0.16+ follow-on once the ledger itself has real usage data, not a v0.15 requirement.
- **Stash vs. commit.** You asked this directly and I don't think there's a clean single answer — it depends on size and license/reuse rights, which a plugin can't infer. Recommend: default to git-tracked (matches the `.gitignore` policy already in use elsewhere in this plugin — nothing else in the vault convention is silently excluded from version control), with an explicit `.gitignore`-style opt-out convention (e.g., a `resources/.local/` subfolder, gitignored, for large binary reference material — audio, big PDFs, images — that shouldn't bloat the repo) documented in `file_hierarchy.md`'s Conventions section the same way the existing scratch-folder convention is documented.
- **What actually goes here vs. stays ad hoc.** This *has* to be assessed per-vault; a plugin can scaffold the mechanism but can't decide content policy for you. Recommend the roadmap ship the mechanism (ledger template, folder, convention doc) and leave "what do we actually save" as an explicit per-vault decision each writer makes once, documented in their own `charter.md`.

**Open question for you:** is the citation ledger meant to track *all* resources/, or specifically external web/API-fetched material (the "stop downloading things over and over" framing suggests the latter — a cache-with-provenance, not a general bibliography)? Those are different scopes — a citation ledger in the academic sense (what's cited in the manuscript) is a different artifact from a fetch-cache ledger (what have we downloaded and when). Worth deciding before building the template, since the schema differs.

## 4. Task dependency gate — design choice, not just "build the locked thing"

Flagging this as a real decision point rather than folding it silently into "finish v0.1.14." The original `ASSESSMENT_DRIFT_ENHANCEMENTS_v014.md` locked **a nightly drift-report warning** for cross-phase dependencies (advisory, surfaced in the hub Attention block, doesn't block anything). The new handoff's Fix 1 proposes **a close-time hard gate** (`pm-close-task` refuses to close unless dependencies are satisfied, requires `--force` to override). These solve related but different problems:

- The locked design catches "a dependency *formed* that changes project shape" — useful for surfacing surprises.
- The new proposal catches "someone is *about to close* a task whose dependency isn't actually done" — useful for preventing the exact I3.2/I3.3 incident (closed, then had to be manually reverted same-day).

The I3.2/I3.3 incident is a close-time failure, not a shape-change-went-unnoticed failure — the nightly-report design as originally locked would **not** have caught it, since the drift check runs on a schedule, not synchronously with the close action. **Recommendation: build both, but recognize they're additive, not redundant** — the close-time gate prevents the specific documented incident; the nightly check catches dependency changes that don't happen to line up with a close event. Also per the 07-22 addendum's correction: this is schema-migration-sized work (`Depends-on` column doesn't exist yet in `todos.md`'s real schema — confirmed against the actual `pm-add-task`/`pm-init-todos` SKILL.md files), not a small patch. Budget it accordingly.
